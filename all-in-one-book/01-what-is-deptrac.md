# 第 1 章：什么是 Deptrac？为什么你需要它？

> 🟢 适合阶段：完全新手
> 
> 阅读时间：约 10 分钟

---

## 1.1 一个真实的痛点故事

假设你是一个 PHP 项目的开发者，你们的项目采用经典的 MVC 架构：

```
src/
├── Controller/    ← 控制器层：处理 HTTP 请求
├── Service/       ← 服务层：业务逻辑
├── Repository/    ← 仓储层：数据库操作
└── Entity/        ← 实体层：数据模型
```

你们团队在文档里写着：**"控制器只能调用 Service，不能直接操作 Repository"**。

一切看起来很美好，直到某天一个新同事为了赶工期，写了这样的代码：

```php
// src/Controller/UserController.php
class UserController
{
    public function __construct(
        private UserRepository $userRepository  // ❌ 控制器直接依赖了 Repository！
    ) {}
    
    public function index()
    {
        $users = $this->userRepository->findAll();  // 绕过了 Service 层
        return $this->render('users/index.html.twig', ['users' => $users]);
    }
}
```

这就是 **架构腐化（Architecture Erosion）** 的开始。

```
    开始时的理想架构                   6个月后的现实架构

    ┌────────────┐                  ┌────────────┐
    │ Controller │                  │ Controller │
    └─────┬──────┘                  └──┬───┬───┬─┘
          │                            │   │   │
          ▼                            │   │   │  ← 各种违规依赖
    ┌────────────┐                  │  ▼   │  │
    │  Service   │                  │┌─────┴──┐│
    └─────┬──────┘                  ││Service ││
          │                         │└──┬──┬──┘│
          ▼                         │   │  │   │
    ┌────────────┐                  ▼   ▼  ▼   ▼
    │ Repository │                ┌────────────────┐
    └────────────┘                │   Repository    │
                                  └────────────────┘
```

## 1.2 架构腐化有多可怕？

| 阶段 | 表现 | 影响 |
|------|------|------|
| 早期 | 偶尔有一两处"走捷径"的代码 | 几乎无感知 |
| 中期 | 越来越多模块相互依赖 | 修改一处牵动多处，测试变困难 |
| 晚期 | 各层边界模糊，循环依赖满天飞 | 无法独立部署、无法拆分微服务、新人上手极难 |
| 末期 | "大泥球"架构 | 只能推倒重写 💀 |

**没有工具监控 = 靠人眼 Code Review = 迟早出问题**

## 1.3 Deptrac 是什么？

**Deptrac** 是一个用于 PHP 的 **静态代码分析工具**，它帮你：

1. **定义**你的架构层次（Layer）
2. **声明**层与层之间的依赖规则（Ruleset）
3. **自动检测**违反规则的代码（Violation）
4. **可视化**你的架构依赖关系

```
┌──────────────────────────────────────────────────────┐
│                    Deptrac 工作流程                     │
│                                                       │
│  ┌─────────┐    ┌──────────┐    ┌──────────────┐     │
│  │  你的    │    │ Deptrac  │    │   分析结果    │     │
│  │ PHP 代码 │───▶│  分析引擎 │───▶│  (违规报告)   │     │
│  └─────────┘    └─────┬────┘    └──────────────┘     │
│                       │                               │
│                       │ 依据                          │
│                       ▼                               │
│                 ┌───────────┐                          │
│                 │  配置文件  │                          │
│                 │ (层+规则)  │                          │
│                 └───────────┘                          │
└──────────────────────────────────────────────────────┘
```

> **一句话定义**：Deptrac 就是 PHP 项目的 **架构规则守护者**。
> 它不改变你的代码，只是告诉你"谁依赖了不该依赖的东西"。

## 1.4 Deptrac 能做什么？不能做什么？

### ✅ Deptrac 能做的

| 能力 | 说明 |
|------|------|
| **定义架构分层** | 把类/接口/函数按正则/目录/接口实现等方式分组为"层" |
| **检测越层依赖** | 发现 Controller 直接用了 Repository 这类违规 |
| **CI/CD 自动检查** | 集成到 GitHub Actions、GitLab CI，PR 违规自动报错 |
| **可视化架构** | 生成 Graphviz 或 Mermaid.js 架构图 |
| **渐进式修复** | 用 Baseline 机制跳过已有违规，只检查新代码 |
| **检测未分层代码** | 找出被遗忘、没有归属于任何层的类 |
| **支持多种架构** | MVC、DDD、Clean Architecture、模块化单体… |

### ❌ Deptrac 不能做的

| 不能做 | 替代方案 |
|--------|---------|
| 检测代码 Bug | 使用 PHPStan / Psalm |
| 代码风格检查 | 使用 PHP-CS-Fixer |
| 运行时性能分析 | 使用 Blackfire / Xdebug |
| 安全漏洞扫描 | 使用 Composer Audit / Snyk |
| 代码覆盖率 | 使用 PHPUnit Coverage |

## 1.5 Deptrac vs 同类工具对比

| 特性 | Deptrac | PHP Arkitect | PHPStan (rules) | PHP Architecture Tester |
|------|---------|-------------|-----------------|----------------------|
| **核心方式** | 配置文件声明层和规则 | PHP 代码写规则 | PHPStan 扩展规则 | PHPUnit 风格测试 |
| **学习曲线** | 低（YAML 配置） | 中（PHP DSL） | 高（需懂 PHPStan） | 中 |
| **可视化** | ✅ Graphviz + Mermaid | ❌ | ❌ | ❌ |
| **CI/CD 集成** | ✅ 原生支持多种格式 | ✅ | ✅ | ✅ |
| **收集器丰富度** | ⭐⭐⭐⭐⭐ 20+ 种 | ⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐ |
| **活跃维护** | ✅ 活跃 | ✅ 活跃 | ✅ 活跃 | ⚠️ 维护中 |
| **Baseline 机制** | ✅ 内置 | ❌ | ✅ | ❌ |

## 1.6 Deptrac 的核心思维模型

在深入学习前，先建立这个思维模型：

```
        ┌─── 你的 PHP 项目有很多类/接口/函数
        │
        ▼
   ┌─────────────────────────────────────┐
   │          第1步：分层（Layer）          │
   │                                      │
   │  "把你的代码分成有意义的组"             │
   │                                      │
   │  例：Controller / Service / Repo     │
   └──────────────────┬──────────────────┘
                      │
                      ▼
   ┌─────────────────────────────────────┐
   │        第2步：定规则（Ruleset）        │
   │                                      │
   │  "声明哪些层可以依赖哪些层"             │
   │                                      │
   │  例：Controller → Service ✅          │
   │      Controller → Repository ❌       │
   └──────────────────┬──────────────────┘
                      │
                      ▼
   ┌─────────────────────────────────────┐
   │        第3步：检查（Analyse）         │
   │                                      │
   │  Deptrac 扫描你的代码，                │
   │  告诉你哪里违反了规则                  │
   │                                      │
   │  输出：✅ 0 violations（恭喜！）       │
   │  或者：❌ 5 violations（需要修复）     │
   └─────────────────────────────────────┘
```

## 1.7 什么样的项目适合用 Deptrac？

### 非常适合 ✅

- 中大型项目（10+ 个开发者，100+ 个类）
- 采用分层架构的项目（MVC、DDD、Clean Architecture）
- 需要长期维护的项目
- 多团队协作的单体应用
- 准备拆分微服务的单体应用（用 Deptrac 先确保模块独立性）

### 可以不用 ⚠️

- 个人小项目（几十个文件）
- 一次性脚本
- 项目即将结束/废弃

### 关键认知

> **Deptrac 不是在出了问题之后才用的工具，而是在项目一开始就应该引入的"架构守护者"。**
>
> 就像你不会等房子塌了再装监控摄像头一样。

## 1.8 本章小结

| 你应该记住的 | 解释 |
|------------|------|
| 架构腐化 | 代码逐渐偏离设计意图，层与层之间产生不该有的依赖 |
| Deptrac 是什么 | PHP 的静态架构分析工具，检测层间违规依赖 |
| 三步工作法 | 分层 → 定规则 → 检查 |
| 不做什么 | 不检测 Bug、不管代码风格、不做安全扫描 |
| 最佳时机 | 项目越早引入越好 |
